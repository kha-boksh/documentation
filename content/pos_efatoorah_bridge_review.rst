تشخيص مشكلة: الفاتورة تعود بدون بيانات من الزكاة والدخل
======================================================

وصف المشكلة
-----------

بعد نجاح الاتصال بين Odoo و API الوسيط لرفع المبيعات/المشتريات، ترجع نتيجة الفاتورة
بدون بيانات مرجعة من الزكاة والدخل (مثل UUID، QR، الحالة، أو رسالة تحقق واضحة).

أين تكمن المشكلة غالبًا؟
------------------------

في هذا السيناريو، الخلل غالبًا **ليس في الاتصال الشبكي الأساسي**، بل في واحدة من ثلاث طبقات:

1. **طبقة بناء الحمولة (Payload Mapping) داخل Odoo**

   - الحقول الإلزامية في XML/JSON غير مكتملة أو غير مطابقة لمواصفات ZATCA.
   - قيم الضرائب (VAT) أو الإجماليات لا تتطابق بين السطور والرأس.
   - تنسيق التاريخ/الوقت أو العملة غير صحيح.

2. **طبقة API الوسيط (Middleware Translation)**

   - الوسيط يستقبل الفاتورة لكنه لا يمرّر كامل استجابة ZATCA إلى Odoo.
   - يوجد تحويل خاطئ لمفاتيح الاستجابة (مثلاً ``result`` بدل ``response``).
   - الـ middleware يتعامل مع رفض ZATCA كنجاح HTTP (200) ويعيد body فارغًا أو مختصرًا.

3. **طبقة معالجة الاستجابة في الموديول (Response Parsing in Odoo)**

   - الكود يتحقق من مفتاح غير صحيح في الرد، فيعتبر النتيجة ``empty``.
   - exceptions يتم ابتلاعها (swallow) ثم إرجاع ``{}`` بدل الخطأ الحقيقي.
   - الحقول المرجعة لا تُحفظ في نموذج الفاتورة/الـ POS Order بسبب write/create mapping.

أكثر الأسباب شيوعًا بحسب الأعراض
-------------------------------

- **نجاح ظاهري + بيانات فارغة** يعني غالبًا:

  - middleware يعيد ردًا غير قياسي.
  - أو parser في Odoo يتوقع schema مختلفًا عن المعاد فعليًا.
  - أو الفاتورة دخلت في ``warning/rejected`` ولم تُعرض تفاصيل الرفض في الواجهة.

Checklist سريع لتحديد السبب خلال 30 دقيقة
------------------------------------------

1. **قارِن 3 سجلات لنفس الطلب**

   - طلب Odoo المرسل (payload النهائي).
   - سجل middleware (الطلب والرد الخام مع ZATCA).
   - ما تم حفظه في Odoo بعد الرد.

2. **افحص كود الحالة والـ body كاملًا**

   - إذا HTTP = 200 والـ body فارغ/ناقص: المشكلة في middleware أو parser.
   - إذا HTTP = 4xx/5xx مع رسالة تحقق: المشكلة غالبًا في payload.

3. **تأكد من الحقول الإلزامية التالية**

   - VAT Number للبائع.
   - نوع الفاتورة والتسلسل.
   - الضرائب على مستوى السطر + الإجماليات.
   - UUID/ICV/PIH (حسب المرحلة Phase 2).

4. **تحقق من السجلات البرمجية (Logs) بالمستويات المناسبة**

   - في Odoo: سجل الرد الخام قبل أي parsing.
   - في middleware: سجل رد ZATCA كاملًا قبل أي normalization.

5. **اختبار إعادة الإرسال لنفس الفاتورة مع idempotency key**

   - إن اختلفت النتيجة بين المحاولات، فهناك مشكلة state/race أو timeout handling.

أماكن الإصلاح المتوقعة داخل الموديول
------------------------------------

- دالة إنشاء payload قبل الإرسال (غالبًا ضمن ``models`` أو ``services``).
- دالة استدعاء API الوسيط (timeouts/retries/status handling).
- دالة parsing للرد وتخزين الحقول المرجعية (UUID/QR/status/errors).
- شاشات/حقول Odoo التي تعرض حالة التكامل (لتجنب إظهار نجاح وهمي).

تحسينات ضرورية لتفادي تكرار المشكلة
-----------------------------------

- عدم اعتبار أي رد ``200`` نجاحًا ما لم يحتوِ الحقول المرجعية المطلوبة.
- توحيد بنية الرد من middleware وإصدار عقد API ثابت (versioned schema).
- حفظ ``raw request/response`` (مع إخفاء الأسرار) لكل فاتورة لتسهيل التتبع.
- إظهار سبب الرفض للمستخدم النهائي بدل ``بدون بيانات``.

الخلاصة العملية
---------------

إذا كان الربط ناجحًا لكن الرد النهائي فارغ، فالمشكلة في الغالب في
**mapping/parsing بين middleware و Odoo** أو في **payload غير مطابق** تم التعامل معه
كسيناريو نجاح شكلي. ابدأ بالمقارنة بين ``raw response`` من ZATCA وما يُحفَظ فعليًا في Odoo،
وستظهر نقطة الفقد مباشرة.
